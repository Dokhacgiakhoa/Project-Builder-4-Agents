Bước 1 / 8Context window

Claude chỉ "biết" những gì đang nằm trong cửa sổ context

Mọi thứ Claude suy luận đều dựa trên một danh sách hữu hạn:

  • Chỉ dẫn hệ thống và CLAUDE.md
  • Lịch sử chat của phiên hiện tại
  • Tool call và output công cụ (test log, grep, cat file…)
  • File đã đọc
  • Mọi nhánh thử nghiệm trước đó, kể cả nhánh đã fail

Vì vậy context không phải nơi "chất đống cho chắc". Nó là một ngân sách cần tiêu có chọn lọc.

Bước 2 / 8Continue hay Clear

Khi nào Continue, khi nào Clear?

Continue

Task tiếp theo dùng trực tiếp phần hiểu biết vừa xây.

Ví dụ: vừa implement một feature xong, giờ viết docs hoặc bổ sung test cho chính feature đó. Claude không phải đọc lại toàn bộ file.

Clear

Chuyển sang bài toán khác về bản chất.

Ví dụ: vừa refactor auth xong, giờ debug một Kafka consumer. Context cũ không còn là tài sản, nó là nhiễu. Anthropic cũng khuyên dùng /clear giữa các task.

Cách tổ chức của đội mình: tách conversation theo mục đích. Một cho implementation, một cho review, một riêng cho investigation hoặc spike kỹ thuật. Reviewer trong context sạch thường sắc hơn vì không bị thiên vị bởi lịch sử debug.
Dùng Claude Code hiệu quả

Ý "reviewer trong context sạch" rất đáng nhấn: cùng một model, nhưng session review riêng bắt được lỗi mà session implement bỏ qua.

Bước 3 / 8Biến Rewind thành phản xạ

Giữ phần "đắt", bỏ phần "độc"

Phản xạ phổ biến khi Claude fail: nhắn tiếp "không đúng, thử cách khác đi".

Cách này giữ nguyên nhánh sai trong context. Sau vài lần, session ngập bởi các hướng đi thất bại và Claude suy luận quanh đống lỗi cũ.

Rewind: quay về ngay sau bước đọc file có ích, loại bỏ nhánh fail, rồi prompt lại với bài học vừa rút ra.

  • Phần đắt: quá trình đọc hiểu codebase.
  • Phần độc: reasoning dựa trên hướng sai.
# prompt sau khi rewind
Đừng dùng approach A vì module đó
không expose API cần thiết.
Đi thẳng sang approach B.

Cơ chế

Mỗi prompt tạo một checkpoint. Nhấn Esc Esc hoặc gõ /rewind, chọn khôi phục conversation, code, hoặc cả hai.

Giới hạn: checkpoint chỉ theo dõi thay đổi qua công cụ sửa file của Claude, không bắt thay đổi từ Bash hay tiến trình ngoài. Rewind không thay thế Git.

Bước 5 / 8Subagent

Subagent là một "phòng sạch"

Agent con có context riêng: đọc rất nhiều file, chạy nhiều công cụ, tạo nhiều output trung gian mà không làm bẩn parent context.

Parent chỉ nhận lại kết luận hoặc báo cáo cuối. Mỗi subagent có system prompt, quyền công cụ và permission độc lập.

Dấu hiệu nên delegate: nếu bạn tự hỏi "mình có thật sự cần toàn bộ output này quay lại main thread không?", câu trả lời thường là không.

Việc hợp với subagent

  • Điều tra một flow kỹ thuật và chỉ trả findings
  • Review diff theo spec và chỉ báo mismatch
  • Viết draft docs từ git diff
  • Tìm edge case hoặc race condition trong một vùng code

Điểm chung: bạn chỉ cần kết quả, không cần giữ toàn bộ quá trình.

Bước 6 / 8Prompt cụ thể

Prompt cụ thể giúp giảm số vòng sửa

Claude suy ra được khá nhiều, nhưng không đọc được suy nghĩ của bạn.

  • Chỉ rõ file hoặc thư mục liên quan.
  • Nêu constraint quan trọng: "tránh mock", "không đổi API public", "giữ backward compatibility".
  • Trỏ tới pattern có sẵn trong codebase nếu muốn Claude làm giống một ví dụ tốt.
  • Mô tả triệu chứng quan sát được thay vì chỉ nêu nhãn chung như "bug login".
Trong src/payments/, thêm retry cho

Bước 8 / 8Spec Kit + Claude Code

Hai lớp, hai vai trò

Spec Kit giữ

"Ý định sản phẩm" và tiêu chí đúng/sai.

Claude Code xử lý

"Đọc code, sửa code, chạy test."

  1. Viết spec trước: problem, mục tiêu, non-goals, user flow, constraint, acceptance criteria.
  2. Cho Claude đọc spec: chỉ explore để kiểm tra tính khả thi, chưa sửa file.
  3. Yêu cầu plan theo spec: file sẽ đổi, rủi ro, dependency, test cần thêm, điểm còn mơ hồ.
  4. Breakdown thành task nhỏ: mỗi task có output rõ và cách verify riêng.
  5. Implement từng task: Clear hoặc session mới cho từng cụm việc, vì spec trong repo đã giữ context chung.
  6. Verify ngược lại spec: đối chiếu implementation với acceptance criteria, liệt kê phần chưa đạt.
Tránh nhầm: spec không thay thế verify. Spec nói rõ "đúng là gì"; Claude vẫn phải chạy test, build, lint để chứng minh implementation đạt spec.

Năm failure pattern thường gặp

Kitchen sink session
Nhồi nhiều task không liên quan vào một thread dài.
Sửa: tách conversation theo mục đích, Clear khi đổi bài toán.
Correcting over and over
Sửa mãi một vấn đề nhưng giữ nguyên các nhánh fail trong context.
Sửa: Rewind, hoặc Clear sau lần sửa thứ hai.
Over-specified CLAUDE.md
File hướng dẫn quá dài làm rule quan trọng bị chìm.
Sửa: "bỏ dòng này Claude có làm sai không?"
Trust-then-verify gap
Thấy "có vẻ đúng" rồi dừng, không verify độc lập.
Sửa: luôn yêu cầu bằng chứng pass/fail.
Infinite exploration
Yêu cầu investigate quá rộng, Claude đọc quá nhiều thứ không cần.
Sửa: giới hạn scope hoặc đẩy điều tra vào subagent.

Ba câu các bạn thường hỏi

Rewind có hoàn tác thay đổi do Bash tạo ra không?

Không. Checkpoint chỉ theo dõi thay đổi qua công cụ sửa file của Claude. Hãy commit thường xuyên; coi Rewind là công cụ dọn context, không phải khôi phục mã nguồn.

Có cần plan cho mọi thay đổi không?

Không. Nếu phải đoán file nào sẽ đổi, hãy plan. Nếu đã liệt kê được file và diff trong đầu, làm thẳng. Với vùng code lạ, plan là cách rẻ nhất để phát hiện đang giải sai bài toán.

Spec Kit có bắt buộc để làm spec-first không?

Không. Bạn có thể tự viết spec, plan, task dưới dạng markdown trong repo, hoặc để Claude phỏng vấn rồi viết SPEC.md. Spec Kit chỉ chuẩn hóa quy trình bằng lệnh và template.
