Architecture Review · checkpoint 03/10

Đầu vào cần có trước khi build
  • Problem và happy path rõ — team biết đang giải quyết việc gì cho ai
  • Scope Must vừa capacity — có estimate và owner cho từng story
  • Architecture có boundary — mũi tên ghi rõ data flow và sync/async
  • Interface contract đủ chia việc — FE, BE và AI có thể code song song
Red flags cần sửa ngay
  • Scope không khớp capacity — quá nhiều Must, chưa tính ngày công tích hợp và test
  • Thiếu interface contract — tuần này không ai làm song song được
  • Tài liệu chưa nằm trên nhánh chính — reviewer không có một nguồn sự thật
  • Ràng buộc in đậm trong đề bị bỏ sót — ràng buộc của đề là Must mặc định, không phải gợi ý
  • PRD lẫn tech term · pain point không số · AC thiếu Given/When/Then — đúng các red flag đã dạy buổi 2
  • Diagram mũi tên trần — không nhãn, không sync/async, không boundary, không lý do chọn component
📊 Team tự đánh dấu từng mục: đạt · cần sửa · blocker — chỉ freeze design khi không còn blocker

Chốt sổ Architecture

Checklist 5 câu — tự chấm lần cuối
  • Cover đủ PRD? — mọi feature Must có chỗ đứng trong diagram
  • Đúng đặc tính task? — task lâu → bg task · cần nhanh → tối ưu latency
  • Có SPOF không? — chết 1 component thì chuyện gì xảy ra
  • Contract đủ rõ để chia việc? — FE/BE/AI nhìn spec là code song song được
  • Effort khớp capacity? — tính theo người và số ngày còn lại, đã trừ tích hợp & test
Từ hôm nay

Design freeze

Architecture đã chốt là hợp đồng làm việc của team. Muốn đổi phải mang đến mentor duty: lý do gì, ảnh hưởng task nào, tốn thêm bao nhiêu ngày — được duyệt mới đổi.

Vì sao khắt khe?

"Nghĩ lại cho hay hơn" ở tuần build là kẻ giết MVP số một. Doanh nghiệp cũng vậy: quyết định có deadline, sau deadline là thực thi — muốn hay hơn, ghi vào backlog bản sau.

🔒 Từ 03/10: đổi architecture = lý do + ảnh hưởng + chi phí → mentor duyệt. Không có ngoại lệ im lặng.

Chia user story — cắt ở đâu?

Công thức cắt
  • 1 story = 1 role + 1 hành động + 1 kết quả quan sát được — role kép hoặc chữ "và" trong hành động = 2 story
  • Đi theo hành trình user qua feature: chỗ nào user THẤY kết quả thì cắt một nhát
  • Bước user không thấy (parse, chunk, embed...) = task kỹ thuật bên trong story, không phải story riêng
3 phép thử — fail 1 là chưa phải story
  • Viết được AC? — 1–3 kịch bản Given/When/Then, không viết nổi = còn mơ hồ, quay lại hỏi PO
  • Demo được? — cuối story chỉ ra được cái gì chạy cho người khác xem
  • Break được ≤ 1 ngày/subtask? — không break nổi = chưa thấy đáy → spike 1 ngày
Ví dụ — feature "Upload tài liệu" (RAG)
feature: Upload & xử lý tài liệu
  US-1 Là nhân viên, tôi upload file và thấy trạng thái xử lý
  US-2 Là nhân viên, tôi xem bảng action item trích xuất được
  US-3 Là quản trị, tôi duyệt field có confidence thấp
# parse / chunk / embed / index → task bên trong US-1, user không thấy

Story quá to? 2 nhát dao thực dụng nhất (SPIDR)

  • Theo path — happy path 1 story · các case lỗi 1 story riêng
  • Theo rule — mỗi rule nghiệp vụ 1 story (log bình thường ≠ cảnh báo ngưỡng)
Story cắt dọc theo giá trị user · task cắt theo việc kỹ thuật · role gán sau cùng

Story → Task — chia theo việc, không theo role

US-1 "Upload và thấy trạng thái" → 5 task
T1 Chốt contract API upload (req/res/error) 0.5d BE+FE cùng chốt
T2 BE: endpoint upload + lưu storage 1d
T3 AI: worker parse tài liệu 1d
T4 FE: màn upload + trạng thái (mock từ T1, song song) 1d
T5 Ghép & test tích hợp 0.5d
# không có task DevOps nào — và thế là đúng: CI/deploy là việc cấp dự án tuần 1
📏 Subtask ≤ 1 ngày · không break nổi = spike 1 ngày rồi mới estimate · task ảo cho "đủ role" = phá estimate
2 task luôn bị quên

T1 — Chốt contract (đầu story)

Cái cho phép BE/FE/AI chạy song song không giẫm chân. Chưa chốt contract mà đã code = tuần sau ghép lại đập đi.

T5 — Ghép & test (cuối story)

Luôn tốn thời gian mà không ai đặt tên cho nó — nên nó ăn vào buổi tối trước demo. Đặt tên, đặt estimate, gán owner như mọi task khác.

Phép kiểm scope: 5 story × 4 task × 1 ngày = 20 ngày công/feature — quỹ thật ~30 ngày → nhân số ra là biết thừa hay thiếu

Mark done — 3 cấp, done là nhị phân

✅ Task done

  • Code + test đi kèm chạy pass
  • PR được review và merge về develop
  • Không còn TODO/hardcode tạm trong phần mình sửa

✅ Story done

  • Toàn bộ AC Given/When/Then pass — chạy thật, không phải "chắc là được"
  • Demo được end-to-end trên môi trường chung, không phải máy cá nhân
  • Không còn bug chặn hành trình chính

✅ Feature done

  • Mọi story Must của feature done
  • AC cấp feature pass + eval đạt ngưỡng (feature AI phải có số)
  • PO/người khác trong team bấm thử được mà không cần người làm ngồi cạnh
🚫 Không tồn tại "done 90%" · "xong trên máy em" · "xong rồi chỉ còn ghép" — chưa demo được trên môi trường chung = chưa done

Project Setup — tuần này phải xong

Repo khớp architecture — nhìn cây = nhìn diagram
repo/
├─ frontend/ # màn hình + gọi API theo contract
├─ backend/
│  ├─ api/ # routes = contract /v1
│  ├─ agent/ # LangGraph flows
│  ├─ rag/ # ingest + retrieval
│  └─ core/ # config · models · repository
├─ tests/ # unit + integration (mock LLM)
├─ eval/ # bộ câu hỏi chuẩn + report
├─ docker-compose.yml # 1 lệnh cả stack
└─ README.md # runbook 15 phút
# mỗi component trong diagram phải chỉ tay được vào 1 thư mục
4 hạng mục — checklist setup
  • Config & secrets — .env + .env.example commit, key thật KHÔNG commit; hardcode key = lỗi 100% sinh viên mắc
  • docker-compose — docker compose up dựng cả stack: ai clone về cũng chạy được y hệt nhau
  • CI tối thiểu — lint + test chạy trên mọi PR; PR đỏ = không merge, không ngoại lệ
  • README = runbook — người mới clone → chạy được trong 15 phút; template BTC trống thì điền hoặc xoá
💰 Setup là khoản đầu tư trả lãi mỗi ngày — tuần này không xong, tuần sau trả nợ gấp 3

Vai trò DevOps — dựng sân cho cả đội đá

Dựng môi trường từ dưới lên
L1 · Infra — VM/cloud, network, domain, firewall: nơi mọi thứ đứng
L2 · Components — Postgres, Redis, vector DB, registry: dựng kèm HA config
L3 · App runtime — container BE/FE build từ template image chung
L4 · Pipeline — CI/CD nối code → env, không ai deploy tay
# dev env dựng xong tuần 1 — test/prod là copy của dev, chỉ đổi config

📥 Nhận requirement từ FE/BE — như một contract

  • Cần env var / secret gì · port nào · healthcheck endpoint nào
  • Phụ thuộc service gì (DB, Redis, LLM API) · cần resource bao nhiêu (RAM model, disk upload)
  • Chốt bằng file: service definition trong docker-compose = contract dev ↔ devops
Template build image — viết 1 lần, mọi service dùng
  • Dockerfile multi-stage chuẩn cho BE (deps → build → runtime mỏng) và FE — service mới chỉ copy template, đổi tên
  • Image không chứa config/secret — 1 image chạy mọi env, config bơm qua env var lúc run
  • .dockerignore đầy đủ — không nhét .env, node_modules, data vào image

🛡️ HA — mặc định, không phải nâng cao

  • Docker: restart: always + healthcheck cho MỌI service · data DB nằm trong volume
  • K8s (nếu dùng): replicas ≥ 2 + liveness/readiness probe
  • Chết là tự dậy — không phải gọi điện cho bạn devops lúc nửa đêm
🎯 Nghiệm thu vai DevOps: "tắt container bất kỳ — hệ tự sống lại không?"

Walking skeleton — chạy trước 10/10

Là gì?

Đường mỏng nhất xuyên hết mọi component

1 màn hình → 1 endpoint → 1 lượt agent trả lời → 1 dòng ghi DB — xấu cũng được, ngu cũng được, nhưng phải chạy end-to-end trên môi trường chung. Sau đó mới làm dày từng khúc.

class DocumentParser(Protocol):
  def parse(self, file: bytes, mime: str) -> ParsedDoc: ...
# constraints:
# - raise ParseError(reason) khi file hỏng — không nuốt lỗi

# - tests/test_parser.py phải pass, không sửa test
Vì sao nhịp này?
  • Người giữ 2 đầu: quyết contract (đầu) và gác chất lượng (cuối) — agent chỉ ở giữa
  • Test viết trước = định nghĩa done cho agent — nó biết lúc nào được dừng
  • Agent code nhanh gấp 10 — đề mơ hồ thì nó code sai cũng nhanh gấp 10
Dành thời gian cho interface — code giờ là phần rẻ nhất, contract là phần đắt nhất để sửa (slide 20 buổi 2)

Luật PR & review

5 luật — dán vào README
  • PR < 400 dòng — quá thì tách; PR to = review lướt = bug lọt
  • 1 PR = 1 task/story — không gộp "tiện tay sửa luôn"
  • Review trong ngày — PR treo qua đêm là chặn đồng đội; review là việc có SLA, không phải việc rảnh mới làm
  • CI đỏ không merge — không có "merge tạm rồi fix sau"
  • Mô tả PR: Closes #n + cách test + ảnh hưởng gì — người review không phải đoán
Review thời coding agent

❌ Approve bằng mắt thường

Lướt 10 giây thấy "code đẹp" rồi approve — code agent sinh ra luôn nhìn đẹp, kể cả khi sai. Đẹp không phải bằng chứng.

✅ Review = chạy thử

Checkout, chạy test, bấm thử happy path + 1 case xấu khi đụng logic chính. Hỏi 1 câu: "case nào làm code này gãy?" — người viết trả lời được mới approve.

Ownership (buổi 1): người approve chịu trách nhiệm ngang người viết

Mock — để không ai ngồi đợi ai

🖥️ FE mock từ contract

  • Stub response đúng theo spec /v1 (msw / json-server / fixture)
  • FE xong trước cả khi BE có thật — ghép chỉ là đổi base_url
  • Contract đổi → mock đổi → FE biết ngay, không đợi tới lúc ghép

🤖 Mock LLM trong test

  • Fake client trả kịch bản cố định: happy · refusal · lỗi timeout
  • Test chạy nhanh, 0 đồng, CI không cần API key
  • Logic quanh LLM (parse output, retry, guardrail) test được như code thường

🗃️ Seed data giả

  • 1 script tạo dữ liệu mẫu: user 2 role, tài liệu, bản ghi lịch sử
  • Ai demo cũng cùng một bộ dữ liệu — hết cảnh "trên máy em có mà"
  • Case xấu trong input spec (file hỏng, đơn vị lạ...) nằm sẵn trong seed
